## Decisão de arquitetura tomada nesta sessão

O usuário perguntou sobre integrar o Plume como renderizador, no modelo do
UnleashedRecomp. Foi apontado que **Plume não resolve desempenho**: é uma RHI, uma
abstração sobre o mesmo Vulkan e, pelo próprio README, o menor denominador comum entre
D3D12/Vulkan/Metal. O ganho daquele modelo vem de **eliminar a emulação do Xenos**, não
do Plume. O `docs/renderer-decision-android.md` já registrava o mesmo ("Plume não resolve
essa tradução").

**Decisão do usuário: manter o renderizador Vulkan do RexGlue e otimizá-lo, cortando o
máximo de traduções.** Não iniciar reescrita para Plume. Não retomar essa discussão sem
o usuário levantá-la.

## O que mudou e foi verificado no aparelho

1. **Aviso de fetch constant deduplicado.** Era o que inviabilizava qualquer diagnóstico:
   a sessão anterior guardou 11 s de log porque 2.372 de 2.377 linhas eram esse aviso.
   Agora 2.394 → 2 linhas, com resumo periódico. Sem tocar em
   `gpu_allow_invalid_fetch_constants`.
2. **`sigqueue(tid)` → `rt_tgsigqueueinfo`.** `sigqueue` endereça processo, não thread.
   4 falhas → 0. Não era a causa da parada.
3. **`X_KTHREAD::kernel_time` (0x58) implementado.** Era `unk_58[0x4]` sem nenhuma escrita
   no SDK, apesar de documentado. Thread "Kernel Time" no `KernelState` o avança a 1 ms.
   **Hipótese testada e descartada: não destravou o jogo.** Mantido por ser correto.
4. **`-O2` em toda a árvore nativa**, guest de `-O1` para `-O2`. Só `rexgpu-xenos` tinha
   otimização. Primeiro quadro −29%, apresentação sob carga +47%. `NDEBUG` **não** foi
   ativado de propósito, para preservar asserts.

## O problema em aberto

O jogo chega à abertura da Rare (peças douradas), renderiza corretamente e **para**.

Estabelecido por medição, não por suposição:

- **Não é travamento gráfico.** O retângulo do jogo é idêntico pixel a pixel em três
  capturas ao longo de 9 s enquanto a GPU apresenta a ~27/s. Swaps contínuos não são
  progresso visual.
- **Não é lentidão.** O `-O2` acelerou tudo e a parada permaneceu no mesmo ponto.
- **Não é o `NtQueryInformationFile(XFileXctdCompressionInformation)`** apontado no recado
  anterior: ocorre 119 vezes mas cessa 18 s antes da parada, e o retorno é igual ao do
  Xenia upstream.
- A `Main XThread` gira a ~100% de um núcleo em `meInternalAlloc`/`meInternalFree`.

**Lead principal para a próxima sessão: despertar perdido entre threads convidadas.**

Releitura de `sub_8264DCD0` (o watchdog do alocador) mostra um segundo caminho de rearme:

```
bl sub_822402A8                      # id da thread atual (3,7% do perfil)
se *(r29+10888) == r3 e *(r29+11004) != 0:
    stw r30,12(r31)                  # rearma o watchdog
```

Enquanto esta thread for a dona do alocador, o watchdog se rearma para sempre — o timeout
é inalcançável por design. Ele **espera progresso de outra thread**. E há **7 `XThread*`
do jogo com zero ticks de CPU em 6 s**, todas em `futex_wait_queue_me`.

Ou seja: as threads que deveriam produzir esse progresso nunca acordam. O bug já corrigido
do `sigqueue` era exatamente dessa família. Procurar outros: entrega de APC, `KeSetEvent`,
semáforos, conclusão de E/S assíncrona.

## Armadilhas que custaram tempo — não repetir

- **O log é acumulativo entre sessões.** Filtrar por timestamp antes de tirar conclusões;
  metade de uma análise foi perdida contando avisos de uma execução anterior.
- **`RuntimeActivity` não é exportada.** `am start -n …/.RuntimeActivity` dá
  `SecurityException`. Ir pela `MainActivity` e tocar "Iniciar Banjo (experimental)".
- **`input tap` é curto demais.** O jogo amostra a ~30 Hz e pode não ver o botão. Usar
  `input swipe x y x y 400`. Conferir os limites por dump da UI: mudam com a orientação.
- **`simpleperf` só funciona via `run-as`**; como shell dá "Permission denied".
- **Git Bash converte caminhos**: usar `MSYS_NO_PATHCONV=1` para `/sdcard/...` e `/proc/...`.
- **PowerShell 5.1**: não redirecionar a saída do `gradlew` com `*>&1 | Tee-Object`. O aviso
  `Picked up JAVA_TOOL_OPTIONS` vira `NativeCommandError` e o build parece ter falhado
  quando na verdade passou.

## Procedimento de perfilagem

```
adb shell run-as org.renut.android /system/bin/simpleperf record \
  -t <tid da Main XThread> -g -f 499 \
  -o /data/data/org.renut.android/perf.data --duration 8
adb shell run-as org.renut.android /system/bin/simpleperf report \
  -i /data/data/org.renut.android/perf.data -g --sort symbol --percent-limit 2
```

O tid sai de `/proc/<pid>/task/*/comm`. Para achar quem gira, comparar `utime+stime` de
`/proc/<pid>/task/*/stat` em duas amostras; o nome da thread contém parênteses, então
parsear a partir do último parêntese de fechamento.
